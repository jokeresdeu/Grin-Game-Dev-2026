# Звіт по лабораторних роботах №3, №4 та №5

## Лабораторна робота №3 - Механіки взаємодії

**Мета:**  
Розширити прототип гри, додавши базові механіки взаємодії, використовуючи `Collider2D`, `Trigger`, `Physics2D.Raycast` та `Physics2D.Overlap*`. Ознайомитись із обробкою подій зіткнень та логікою взаємодії між обʼєктами.

### Реалізація

- Обрана гра: **Classic Platformer**
- У межах лабораторної було реалізовано та доповнено основні механіки взаємодії між гравцем, ворогами та об’єктами рівня.

### Додані механіки

- **Система здоров’я (HP)**  
  Гравець має обмежену кількість здоров’я, яке зменшується при отриманні шкоди від ворогів або небезпечних об’єктів.

- **Система досвіду (EXP) та рівнів**  
  Гравець отримує досвід за певні дії у грі, а після досягнення необхідного значення переходить на новий рівень.

- **Умова смерті**  
  Гравець помирає при втраті всього здоров’я, падінні у яму або потраплянні під небезпечні об’єкти.

- **Перезапуск сцени**  
  Після смерті з’являється меню програшу з можливістю перезапуску рівня.

- **Ворог**  
  Реалізовано базову бойову взаємодію з ворогом: атака гравця, отримання шкоди, анімація пошкодження/смерті.

- **Небезпечні об’єкти середовища**
  - Вогонь, який завдає **періодичної шкоди**
  - Шипи, які можуть **вбивати гравця**
  - Яма, при потраплянні в яку гравець **гине**

- **Механіка ключів і дверей**
  - Додано **збір ключів**
  - Двері можуть відкриватися:
    - після збору потрібної кількості ключів
    - через взаємодію з **ричагом**
  - Після відкриття дверей гравець може перейти на **наступну сцену**

### Використані типи колізій

У проєкті використано такі типи перевірки взаємодії:

- `Collider2D`
- `Trigger`
- `Physics2D.OverlapCircle`
- `Physics2D.OverlapCircleAll`

### Де застосовано `Raycast` або `Overlap`

- `Physics2D.OverlapCircle` використовується для:
  - перевірки, чи стоїть гравець на землі
  - перевірки наявності стіни для механіки ковзання по стіні

- `Physics2D.OverlapCircleAll` використовується для:
  - пошуку ворогів у зоні атаки гравця

- `Trigger` використовується для:
  - збору ключів
  - відкриття дверей
  - активації ричага
  - перевірки попадання у небезпечні зони (вогонь, яма, шипи)
  - переходу між сценами

### Чому було обрано саме такі методи перевірки

Для платформера `OverlapCircle` та `Trigger` є зручними й ефективними, оскільки:

- дозволяють просто реалізувати перевірку близьких об’єктів
- добре підходять для 2D фізики
- не потребують складної логіки обчислень
- легко інтегруються в бойову систему, платформінг і взаємодію з оточенням

### Вплив механік на core loop

Реалізовані механіки напряму формують **core loop** гри:

1. Гравець досліджує рівень
2. Уникає пасток і бореться з ворогами
3. Збирає ключі та взаємодіє з об’єктами
4. Відкриває двері та переходить далі
5. Отримує досвід і посилює персонажа

Таким чином, механіки підтримують цикл:  
**рух → дослідження → бій → уникнення небезпек → збір ресурсів → прогрес по рівню**

## Лабораторна робота №4 - Анімації в Unity

**Мета:**  
Додати анімації для гравця та об’єктів сцени, керуючи станами через код.

### Реалізація

У межах лабораторної роботи було проанімовано як самого персонажа, так і частину інтерактивних об’єктів рівня.

### Проанімував мінімум 5 обʼєктів

#### Гравець
Для гравця реалізовано такі анімації:

- `Idle`
- `Run`
- `Jump`
- `Attack`
- `Roll`
- `Hurt`
- `Death`
- `Block` *(візуальна анімація без окремої бойової логіки)*

#### Вороги
Для ворогів реалізовано:

- `Idle`
- `Attack`
- `Death`

#### Інтерактивні об’єкти та середовище
Було додано анімації для:

- ключа при підборі
- шипів / небезпечних пасток
- декоративних об’єктів сцени
- меню та UI-елементів

### Керування анімаціями через код

Керування анімаціями реалізовано за допомогою компонента `Animator` та параметрів стану.

Зокрема:

- перемикання між `Idle` і `Run` залежно від руху
- запуск `Jump` при стрибку
- запуск серії `Attack` при атаці
- запуск `Roll` при перекаті
- запуск `Hurt` при отриманні шкоди
- запуск `Death` при смерті
- активація допоміжних станів (`Grounded`, `WallSlide`, `AirSpeedY`, `AnimState`) для синхронізації руху та анімації

### Результат

Завдяки анімаціям гравець та об’єкти сцени стали візуально зрозумілішими, а ігровий процес — більш живим і читабельним.  
Стан персонажа тепер добре відображається не лише через механіку, а й через візуальну реакцію.

## Лабораторна робота №5 - UI

**Мета:**  
Створити ігровий UI для індикації стану гравця та управління грою.

### Реалізація

У межах лабораторної було додано базові елементи інтерфейсу для взаємодії гравця з грою та відображення поточного стану персонажа.

### Додані UI елементи

- **Індикатор здоров’я (HP)**  
  Реалізований через `Image.fillAmount`, оновлюється при отриманні шкоди або лікуванні.

- **Індикатор досвіду (EXP)**  
  Також реалізований через `Image.fillAmount`, оновлюється при отриманні досвіду.

- **Відображення рівня гравця**  
  Реалізовано через `TMP_Text`.

- **Лічильник ключів**  
  Додано UI-елемент, який показує:
  - скільки ключів уже зібрано
  - скільки ключів потрібно для відкриття дверей

- **Меню смерті**
  - відображається після смерті персонажа
  - містить кнопку перезапуску сцени

- **Головне меню**
  - стартова сцена гри
  - можливість запуску гри

### Реалізовані класи для керування UI

Для оновлення UI створено та використано окремі скрипти, зокрема:

- `PlayerView`
  - оновлює HP
  - оновлює EXP
  - оновлює рівень

- `KeysUI`
  - відображає кількість зібраних ключів
  - показує необхідну кількість ключів для відкриття дверей

### Взаємозв’язок UI з ігровою логікою

Інтерфейс синхронізований із поточним станом гри:

- при втраті HP оновлюється смуга здоров’я
- при отриманні досвіду оновлюється EXP bar
- при підборі ключів змінюється лічильник ключів
- при смерті відкривається меню програшу

### Результат

Завдяки UI гравець постійно отримує зворотний зв’язок про свій стан, прогрес та умови проходження рівня.  
Це покращує зручність гри та робить ігровий процес зрозумілішим.
